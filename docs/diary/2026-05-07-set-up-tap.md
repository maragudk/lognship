# Diary: Set up Tap to replicate lognship records into a local index

Background research and a first running deployment of [Tap](https://atproto.com/blog/introducing-tap) — Bluesky's new sidecar that subscribes to a relay, validates and verifies records, and re-emits filtered JSON events for one app to consume. The goal is to use Tap as the entry point to a separate local read-model so the web app can eventually browse projects, members, repos, and log entries without round-tripping to PDSes for every page render. This session covered the research, the docker-compose config, and a smoke test by publishing a new `com.lognship.actor.profile` from a second account.

No code shipped — only infra config (in a separate repo) and one new atproto record. The lognship Go codebase wasn't touched.

## Step 1: Research Tap and pick a fit for lognship

**Author:** main

### Prompt Context

**Verbatim prompt:** "Look into TAP and how we could use that to replicate everything from our lexicons across PDS'es into a local SQLite database (probably separate from our main app database) and how we could then add the changes to our app, so we can browse projects, members, log entries etc. online on the web app. Don't write any code yet. https://atproto.com/blog/introducing-tap"
**Interpretation:** Open-ended architecture research. Read the blog post, read the indigo README, sketch how Tap slots into lognship, propose a read-model schema, flag decisions. Don't write code yet — Markus wants alignment first.
**Inferred intent:** Markus has been hand-rolling everything (lexicons, records via goat). Tap is a chance to skip the firehose plumbing and jump straight to "give me typed JSON events for my collections." He wants to know whether that path is real, what sits on either side of it, and what choices it forces.

### What I did

Pulled the Tap blog post and `indigo/cmd/tap/README.md`. Wrote up a one-page architecture: Tap as a sidecar (single Go binary, SQLite, port 2480), three delivery modes (websocket-with-acks default, fire-and-forget, webhook), at-least-once with strict per-repo ordering. Sketched a read-model `index.db` separate from `app.db`, with one table per record type keyed by `(did, rkey)` and `cid` for idempotency, plus a `tracked_repos` table for our ack cursor. Listed five decisions worth flagging — sidecar vs library, webhook vs websocket, full-network vs DID-set, separate db file vs reuse, whether to also index `app.bsky.actor.profile`.

Then a multi-turn debate about which collection should be Tap's `TAP_SIGNAL_COLLECTION`:
- I initially recommended `com.lognship.project` — owners only, smallest set, requires a discovery loop to add members from membership records.
- Markus pushed: "why not actor.profile?" I argued profile-as-signal would track lurkers without browseable content. Defensible for now, but…
- He countered: "what about log.entry?" I switched the recommendation — entry-as-signal catches every active contributor directly, including ones not formally declared as members, and the project owner is reached via the entry's `project` AT URI.
- Then he dropped the deciding constraint: the webview always creates a `com.lognship.actor.profile` on first login. With that guarantee, profile-as-signal becomes the cleanest choice — it tracks every webview user the moment they touch the app, and the discovery loop disappears entirely. We landed there.

### Why

The signal collection determines the boundary of what Tap considers "interesting" on the network. Three options each had a different invariant:
- `project` = "owners are interesting; everyone else is reached via membership records."
- `log.entry` = "anyone who has written something is interesting; owners are reached via the entry's project ref."
- `actor.profile` = "anyone who has logged in is interesting."

The right answer depends on entirely on whether `actor.profile` is a reliable proxy for "lognship user." Markus's webview-creates-on-first-login rule makes it one. Without that rule it's a noisy signal; with it, it's the tightest one available.

### What worked

Each turn of the signal-collection debate flipped the recommendation cleanly because the underlying decision wasn't preference, it was a fact about the system that I didn't have. Once Markus surfaced the webview-on-first-login constraint, the answer fell out without further argument. Worth remembering: when the recommendation is wobbling between options, it's usually because a system invariant is missing, not because the options are equally good.

### What didn't work

Bluesky's documentation for the websocket ack protocol on `/channel` is implementation-defined (the README says "use a client library such as `@atproto/tap`" — which is TypeScript). For Go consumers, the only authority is the indigo source itself. We dodged this for now by deferring the consumer entirely; future work will need to either reverse-engineer it or use webhook mode.

### What I learned

`TAP_SIGNAL_COLLECTION` only takes one collection — singular, not plural. So you can't have "project OR entry" as a combined signal; you pick one and use the discovery loop to fan out from there. That constraint shaped the whole debate.

`com.atproto.sync.subscribeRepos` is the firehose endpoint that Tap subscribes to. The relay default is `relay1.us-east.bsky.network`. There is no Bluesky-operated EU relay (DNS-probed several plausible hostnames; only `us-east` and `us-west` resolve). Latency from Frankfurt is ~80-100ms, which doesn't matter for a bulk firehose stream.

### What was tricky

The architecture sketch tried to design a future read-model schema (`projects`, `repos`, `memberships`, `log_entries`, etc.) before any code was being written. Speculative — but Markus had asked for it explicitly and it forced the cross-repo-reference question into the open: a `log.entry` references its project by AT URI, but the project record lives in a different repo, and Tap orders only within a repo. So the read-model has to tolerate dangling AT URI references and resolve them lazily as the parent records arrive. Cheap to design for, expensive to retrofit.

### What warrants review

The proposed `index.db` (separate from `app.db`) is a schema sketch on paper, not committed code. Reviewers should challenge: do we actually need two SQLite files, or is a separate `tap.*` table prefix in `app.db` enough? The argument for separation is that `index.db` is fully rebuildable from PDSes (delete and resync) while `app.db` holds irreplaceable session/auth data — different durability requirements. Markus's earlier feedback on `app.db` naming was that we don't *rename* it, not that we can't have a sibling, so a second file is allowed. But this is the kind of decision a teammate might prefer to defer until the indexer is being written.

### Future work

The websocket-with-acks consumer in Go. Webhook mode is simpler to start (HTTP handler, JSON in, 200 ack out) and may be the right v1 even though it adds a hop. The full read-model schema can be derived from the lexicons themselves once a code-generation step is in place; deferred until the consumer exists.

## Step 2: Build the docker-compose config

**Author:** main

### Prompt Context

**Verbatim prompt:** "I lean towards using the log entry as signal. What else do I need to set up Tap in my docker compose config?"
**Interpretation:** Concrete config-writing now that we'd settled the architecture. Markus said "in my docker compose config," which I initially read as adding to lognship's compose; he corrected with "(Not in this project, it's infra)" — Tap lives in a separate infra repo.
**Inferred intent:** Get to a minimal, runnable compose service block. Iterate on it.

### What I did

Started with a "kitchen sink" config showing every relevant env var. Markus then trimmed it in five passes:
1. "leave out all optional env vars" — dropped `TAP_BIND`, `TAP_RELAY_URL`, `TAP_PLC_URL`, `TAP_LOG_LEVEL`, all the perf knobs.
2. "add database url and volume back" — those two are technically optional (defaults exist) but coupled to persistence.
3. "restart: always" — explicit policy.
4. "Drop the webhook URL, we don't have a webhook yet" — switched to websocket default, knowing nothing's consuming yet.
5. "There is nothing writing data yet, there are only a few records" — confirming the no-consumer outbox pressure was a non-issue.
6. "Do I need the admin password now?" — no; without it the admin endpoints are unauthenticated, fine on internal docker network.
7. "I'd like to bind to /root/data/tap/ instead of a volume" — switched named volume to bind mount.

I also went looking for the newest published `sha-*` image tag. The indigo repo's `:latest` tag for `ghcr.io/bluesky-social/indigo/tap` resolves cleanly, but I wanted a pinned digest. Pulled the GHCR token, listed all `sha-*` tags (71 of them), and matched each against the digest of `:latest`. The match was `sha-4f47add43060c27e8a37d9d76482ecddf001fcd8`, which corresponds to indigo commit "Tap: no firehose replay mode" from 2026-03-11. Notably this is *not* the head of indigo's main branch — Tap doesn't get a fresh image on every commit, which is worth remembering when bumping.

I also inspected the image's container config (manifest → config blob) to check `WorkingDir`. It's `/data`, which means the default `TAP_DATABASE_URL=sqlite://./tap.db` resolves to `/data/tap.db` — exactly where the bind mount lands. So `TAP_DATABASE_URL` itself can be dropped too. Markus didn't ask but I noted it.

The final config:

```yaml
services:
  tap:
    image: ghcr.io/bluesky-social/indigo/tap:sha-4f47add43060c27e8a37d9d76482ecddf001fcd8
    restart: always
    environment:
      TAP_SIGNAL_COLLECTION: "com.lognship.actor.profile"
      TAP_COLLECTION_FILTERS: "com.lognship.*"
    volumes:
      - /root/data/tap:/data
```

### Why

Markus's iterative-trim style is consistent: start somewhere, ask "is this needed?" for each piece, drop everything that earns nothing. The config is now four lines of meaningful config (one signal, one filter, one bind mount, one image pin), and the implicit defaults take care of the rest. Pinning by digest-via-sha-tag is the right idea for beta software; latest-tag-following is asking for a 3am surprise.

### What worked

Cross-referencing tag list against `:latest`'s manifest digest worked. GHCR's tags-list endpoint returns tags in arbitrary order — registries don't sort by recency — so I couldn't just take the last one. Walking each manifest until the digest matched was reliable, and getting through 71 tags took a few seconds.

### What didn't work

My initial assumption that the newest `sha-*` tag would correspond to indigo's main branch HEAD was wrong. The current main HEAD (`ce62b8f`, 2026-04-28) has *no* tap image — `HTTP 404` on the manifest. Tap is built on a subset of commits, presumably tied to its own subdirectory's CI workflow. Don't assume one-image-per-commit.

### What I learned

When using docker-compose's short volume syntax, an absolute path on the left side (`/root/data/tap:/data`) is automatically a bind mount. Named volumes are the case where the left side is a bare name. No `type: bind` needed in the long form unless you want explicit clarity.

Tap's `WorkingDir` is `/data`, which is unusual but convenient — it means the default sqlite URL "just works" with a `/data` bind mount and no `TAP_DATABASE_URL` env var.

### What was tricky

Distinguishing "optional in the docs" from "optional in practice." `TAP_DATABASE_URL` has a default, so it counts as optional. But if you don't set it *and* don't bind-mount to `/data`, the database lands in the container's writable layer and gets discarded on every restart, which means a full network re-backfill. The pair "set the env var" / "bind-mount the path" is functionally a single decision — keep both or drop both — and I should have been clearer about that in the trimming passes.

### What warrants review

The image pin: `sha-4f47add43060c27e8a37d9d76482ecddf001fcd8`. It's the current `:latest` digest as of this session; before bumping, repeat the digest-match procedure rather than blindly using the next `sha-*` tag. The bind path `/root/data/tap` assumes a server with that filesystem layout — confirm the host has it, and that the host directory's UID matches Tap's runtime UID (the image runs as root inside, so this is unlikely to bite, but worth knowing).

### Future work

When the lognship consumer comes online, this config grows: `TAP_WEBHOOK_URL` (or websocket dial-out from lognship) and `TAP_ADMIN_PASSWORD` come back as required, along with networking glue between the two compose services.

## Step 3: Smoke-test by creating maragubot's actor.profile

**Author:** main

### Prompt Context

**Verbatim prompt:** "Let try creating an actor.profile for you, maragubot. See @bin/goat-as"
**Interpretation:** Stand up a second tracked DID by publishing a `com.lognship.actor.profile` from the maragubot account, and verify Tap picks it up via the firehose. Use the `bin/goat-as` profile-switching helper to act as maragubot rather than lognship.
**Inferred intent:** End-to-end verification. The lognship.com DID was already tracked from the very first start (it had a `com.lognship.actor.profile` from a prior session). Markus wants to see Tap's signal-collection-driven discovery actually work for a *new* DID — not just for the one already in its db.

### What I did

Read `bin/goat-as` and confirmed the maragubot profile was saved (DID `did:plc:ccrzw4q3x5cknyo5uqsti74x`, on Bluesky's `phellinus.us-west.host.bsky.network`). Wrote a profile JSON with `displayName: "maragubot"`, a one-line dry-humor description, the github URL as website, and a fresh `createdAt`. Validated locally first — Markus interrupted to insist on this — using `goat lex validate --catalog lexicons/com /tmp/maragubot-profile.json`. The first attempt failed with `unsupported lexicon language version: 0` because the catalog directory included `lexicons/testdata/` (test fixtures, not real lexicons); narrowing to `lexicons/com/` made it pass.

Then `goat record create --rkey self`. The PDS rejected with `HTTP 400: InvalidRequest: Unknown lexicon type: com.lognship.actor.profile`. Bluesky-operated PDSes only accept records whose lexicons they have cached; lognship's lexicons are published to the lognship.com repo but Bluesky's PDSes don't refresh from arbitrary sources. Retried with `--no-validate` and the record went through:

```
at://did:plc:ccrzw4q3x5cknyo5uqsti74x/com.lognship.actor.profile/self
bafyreid2uswioxphpcksrblkt6m6yzjpdbagtevnsplto7la5vuubiimki
```

Tap's logs confirmed it picked up the new DID about 70 seconds later — enumerated the new repo from `phellinus.us-west.host.bsky.network` (a 28KB CAR, larger than lognship.com's 11KB because maragubot also has a Bluesky post history), parsed it, completed resync. Repository now tracked.

Markus then corrected the website value — should be `www.maragubot.com`, not the github URL. Wrote a new JSON, validated, and used `goat record update --rkey self` to replace the record. New CID, same AT URI. Saved a memory entry recording maragubot's DID, PDS, website, and goat profile name so future sessions don't conflate the website with the GitHub username.

### Why

Smoke testing the signal-collection path on a *fresh* DID is materially different from seeing the bootstrap backfill of the lognship.com account. The bootstrap was Tap's network-enumeration crawler finding the existing record on first run; the maragubot test was Tap reacting to a brand-new firehose event for a DID it had never seen before. Confirming the second path is what proves the system will pick up new lognship users as they sign up.

### What worked

End-to-end latency from `goat record create` → "resync repo complete" was about 70 seconds. Dominated by relay propagation (Bluesky's relay batches firehose events) and PDS-side fetch. That's a fine steady-state number for an indexer that's not on a hot path.

Local validation against the lognship lexicon catalog caught any schema errors before going over the wire — turn-around was a fraction of a second compared to the network round-trip needed to see a PDS-side rejection. Worth keeping in muscle memory.

### What didn't work

The PDS rejection was unexpected the first time. Bluesky's official documentation for "publishing your own lexicon and using it" implies that DNS NSID resolution makes the lexicon discoverable — it does, for clients reading records, but not for the source PDS doing write-time validation. Bluesky-hosted PDSes only validate against lexicons they've been told about. There's no mechanism (yet) for them to dynamically resolve a custom lexicon at write time. `--no-validate` is the documented escape hatch, and it's safe in our case because we'd already validated locally with the same schema.

The `goat lex validate --catalog lexicons` invocation failed because the catalog walker doesn't skip the `testdata/` subdirectory. Pointing at `lexicons/com/` worked, but a glob like `lexicons/com/lognship/**/*.json` would have been safer and more explicit. Worth filing as a goat ergonomics nit.

### What I learned

Bluesky PDS lexicon caching is a real operational concern for custom lexicons. Until/unless Bluesky's PDSes start resolving NSIDs at write time, every lognship write from a Bluesky-hosted PDS needs `--no-validate`. Self-hosted PDSes that resolve lexicons dynamically (or that ship the lognship schemas in their catalog) wouldn't have this issue. This is a fact worth saving as memory; it'll come up every time we publish a lognship record from a Bluesky PDS account.

The `goat-as` helper composes nicely with arbitrary goat commands: `goat-as <profile> -- <subcommand...>`. The `--` separator is mandatory; without it the script bails with "expected '--' before command." Predictable, safe.

### What was tricky

Profile-record convention: when updating a record, do you bump `createdAt`? No — `createdAt` is the original creation timestamp, set once and immutable. Only the CID and the record body change on update. I kept the original timestamp on the website fix; this is the right pattern for any "self" record that represents a long-lived identity rather than an event.

The website confusion (`github.com/maragubot` vs `www.maragubot.com`) was a minor but real failure mode. The github username and the maragubot persona share a name but aren't the same thing. Saved a memory entry to make sure I don't conflate them again.

### What warrants review

The `--no-validate` write to the PDS. The local validation passed against the same lexicon, so the record body is well-formed — but a reviewer should still confirm the AT URI resolves correctly and the JSON parses, because `--no-validate` removes the safety net entirely. Quick check: `goat record get at://did:plc:ccrzw4q3x5cknyo5uqsti74x/com.lognship.actor.profile/self`.

### Future work

If we self-host a PDS for lognship users (which is a plausible direction), the `--no-validate` workaround disappears entirely — that PDS would either ship lognship's lexicons in its catalog or resolve them at write time. Not a v1 priority, but worth noting as a knock-on benefit of running our own PDS.

A related cleanup for goat: filing or contributing a fix so `goat lex validate --catalog <dir>` skips `testdata/` (or any subdirectory that doesn't look like a lexicon root) instead of refusing the whole tree. Out of scope for lognship; noting only because it bit us in this session.
